# Integration handoff

The workspace-local `contracts.v1` package contains canonical ports and DTOs; root contracts are unchanged. Identity provides `CurrentActorPort`, orders provides `OrderSnapshotPort`, and routing provides `RouteSnapshotPort`. Billing exposes local freight lookup and simulated payment ports in `logistics.shared` to orders; consumers do not query billing tables. Replace dev/test `Fixtures` with Pessoa 2 and 3 implementations of partner, fleet, delivery, notification and document ports. Calls use Java ports, not cross-module SQL or HTTP.

Confirmation and assignment persist local reconciliation state and use stable event IDs. Assignment can return 503 after the fleet reservation succeeds; retry the same route, or allow the scheduled retry to finish. Start is blocked while delivery assignment remains pending. The delivery contract has no command to transition deliveries to in-transit on route start; that transition remains Pessoa 3's responsibility until the shared contract is extended through the agreed process.

The dev-only replay first rebuilds confirmation fakes, then restores fake fleet and deliveries for assigned and in-progress routes. These in-memory fakes are not durable real fleet or delivery implementations. The fake has one driver/vehicle and refuses multiple active reservations. Route stops currently have an unconditional order uniqueness constraint: route completion/cancellation and releasing that constraint for a terminal route remain future lifecycle work.

Flyway migrations V5 and V6 extend V1–V4 without changing them; coordinate global version allocation before shared integration. Freight tariff and geocoding provider remain deployment/business decisions. Set `FREIGHT_TARIFF_PER_KM` explicitly for new quotes; confirmed order quotes are immutable and remain readable without configuration or OSRM. `ROUTING_PROVIDER=fake` is dev/test only, while OSRM is the default. See README for runtime settings and the offline test command. No P2/P3 business implementation is supplied here.

## Offline limitations and recovery

The fleet fake validates route and order snapshots before taking its in-memory reservation lock; its single vehicle is reserved atomically within that process. The fleet call still occurs during the local route SQL transaction. If SQL assignment or commit fails after the fake reserves, the in-memory reservation remains while the route stays planned. Retrying the same route reuses the reservation; another route may see `NO_ELIGIBLE_RESOURCE` until recovery or a process restart. There is no contract operation to undo this failed assignment, so this is not distributed atomicity. Real adapters need durable idempotent reservation and reconciliation for this failure window.

Scheduled order and route reconciliation retains pending work after failures and logs the object ID and safe error code, without exception payloads. Retry uses stable IDs; a 503 after local confirmation or assignment does not imply rollback. Run offline tests with `ROUTING_PROVIDER=fake`; never use the fake routing provider in production.

The fake fleet release validates a completed route before freeing its one vehicle. It deduplicates releases by route, not by event ID or event payload; full event-level conflict and retry semantics remain for the real fleet adapter. The snapshot check and in-memory reservation update are not a distributed transaction.
