# Integration handoff

The workspace-local `contracts.v1` package contains the canonical port interfaces and DTOs; it does not modify root contracts. `identity` supplies JWT-backed `CurrentActorPort`; `orders` supplies `OrderSnapshotPort`. Replace the dev/test `Fixtures` adapter with the owning modules' implementations of `PartnerLookupPort`, `FleetAssignmentPort`, `FleetReleasePort`, `DeliveryCommandPort`, `DeliveryStatusPort`, `NotificationRequestPort` and `DocumentRequestPort` during integration. The routing schema is present, but `RouteSnapshotPort` has no implementation until routing is built. Exchange Java DTOs in process, not HTTP or cross-module table queries. The internal simulated payment port delegates to the billing adapter within the confirmation transaction.

The order database stores a stable confirmation event and delivery/notification completion flags. An unsuccessful call is retried with the same event ID; adapters must enforce their own durable idempotency. Notifications without a recipient are marked ineligible instead of inventing an address. Dev fixtures are process-local, deterministic IDs and timestamps and deliberately lose state on restart; the dev startup listener reopens the orders-owned confirmation jobs and replays the original events to restore delivery/notification fake state. Assignments are not restored. Real adapters must persist their own state and provide their own reconciliation guarantees. The fake document succeeds only for a quoted order, and the fake route assignment is a fixture, not the fleet allocation implementation.

Flyway versions V1–V4 are workspace-local; coordinate global allocation before applying shared migrations. Late cancellation, freight tariff and geocoding remain business decisions; confirmed cancellation is blocked. No migration under root contracts or global CI is modified.
